### M2 Tool Deliverables

1. **`tools/biolat/`**: Rust eBPF tool using libbpf-rs. BPF program (`biolat.bpf.c`) attaches to `block_io_start`/`block_io_done` tracepoints, measures IO latency, outputs a log2 histogram. Userspace (`main.rs`) loads the skeleton, attaches programs, and prints the histogram on exit.

2. **`docs/M2-biolat-design.md`**: design note covering technology selection, architecture, tracepoint selection rationale, verification results, and known limitations.

3. **`scripts/verify_m2.sh`**: fixed-parameter fio workload (32M of 4K direct writes via libaio, iodepth=8, on a block-backed filesystem), 5 runs, runs biolat and bcc `biolatency-bpfcc` in parallel, compares peak bucket positions (acceptance: within 2x).

## Deviations from ROADMAP

1. **libbpf-rs version**: used 0.25.0 from crates.io (matching the Debian package version). The ROADMAP mentions `libbpf-cargo` for skeleton generation; we used the `SkeletonBuilder` API from libbpf-cargo 0.25.0.

2. **Tracepoint selection**: initially used `block_rq_issue`/`block_rq_complete` (as described in the plan), but switched to `block_io_start`/`block_io_done` because the former had unreliable sector matching on this kernel. The `block_io_*` tracepoints are the same ones bcc biolatency uses on modern kernels.

3. ~~**dd instead of fio**~~ (retracted during M2 review): an earlier version of this report claimed that `fio` with `ioengine=libaio` did not generate block IO tracepoint events on this VM's virtio disk, and verification used `dd oflag=direct` instead. Re-testing showed the actual cause: the workload file was placed in `/tmp`, which is a **tmpfs** mount — tmpfs IO never reaches the block layer, so no `block_io_*` tracepoints fire regardless of the workload tool. With the workload file on a block-backed filesystem (`/var/tmp`, ext4 on vda), fio/libaio with `direct=1` generates block IO events correctly, and `verify_m2.sh` now uses fio as the ROADMAP specifies. This deviation no longer exists.

4. **bcc biolatency `-d` flag**: required the `-d vda` device filter to avoid a hang in `BPF.get_kprobe_functions()` on kernel 6.12. This is a known BCC issue on newer kernels.

5. **Generated skeleton**: used `cargo-libbpf` (installed via `cargo install libbpf-cargo`) for skeleton generation, and `SkeletonBuilder` in `build.rs` for build-time compilation. The generated `biolat.skel.rs` is not checked into git (it's in `target/`).
