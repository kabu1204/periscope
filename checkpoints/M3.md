# M3 Checkpoint Report

## Deliverables

1. **`tools/runqlat/`**: Rust eBPF tool using libbpf-rs, equivalent to bcc `runqlat`. BPF program (`runqlat.bpf.c`) attaches to `sched:sched_wakeup`, `sched:sched_wakeup_new`, and `sched:sched_switch` tracepoints, measures run queue latency per task, outputs a log2 histogram in microseconds. Handles preemption (`prev_state == TASK_RUNNING`) the same way bcc does.

2. **`tools/offcpu/`**: Rust eBPF tool using libbpf-rs, equivalent to bcc `offcputime`. BPF program (`offcpu.bpf.c`) attaches to `sched:sched_switch`, accumulates off-CPU microseconds per (pid, comm, kernel stack, user stack). Userspace symbolizes kernel stacks from `/proc/kallsyms`; user addresses printed raw. Idle task excluded (same as bcc).

3. **`scripts/verify_m3.sh`**: oracle comparison + three injection scenarios (workloads in `scripts/m3/`):
   - Scenario A: CPU saturation (`cpu_burn.sh`) — runqlat tail (>=64us) fraction must rise >=4x vs idle baseline; peak and tail compared to bcc runqlat within 2x.
   - Scenario B: lock contention (`lock_contention.c`, 8 threads on one mutex) — offcpu and bcc offcputime must both attribute to the futex stack.
   - Scenario C: synchronous disk wait (`sync_write.sh`, fio sync direct IO on block-backed fs) — offcpu must attribute to the IO wait stack.

4. **`docs/M3-design.md`**: design note with principles, architecture, verification, and a "how to manually verify" checklist.

5. **`ci_report.sh` M3 section**: cargo fmt, clippy, build for both crates, plus `scripts/verify_m3.sh`.

## Deviations from ROADMAP

1. **runqlat oracle comparison metric**: the ROADMAP requires "magnitudes consistent (deviation < 2x)". The peak bucket alone is not a valid signal for runqlat — woken daemons produce many short waits that keep the peak low even under CPU saturation, for bcc as well as our tool. The comparison therefore uses both peak bucket position and the fraction of samples at or above 64us; both must be within 2x. The saturated distributions match closely.

2. **bcc warmup**: `runqlat-bpfcc` needs ~1–2s for LLVM compilation before it starts tracing. `verify_m3.sh` waits for its "Tracing" banner before starting the workload so both tools observe the same window.

3. **offcpu user stacks not symbolized**: user-space addresses are printed raw. Attribution to known kernel stacks (futex, IO wait) — which is what the scenarios check — is unaffected. bcc resolves user symbols via debug info; that is a future enhancement.
